# Backup and Restore

How Orgistry backs up its durable state, how a restore is proven to work, and
exactly which parts of a production backup story this repository does **not**
provide.

Companion documents: [pitr.md](pitr.md) (point-in-time recovery),
[retention.md](retention.md) (data lifecycle and cleanup),
[deployment-artifacts.md](deployment-artifacts.md) (the API artifact this
recovery contract ends at).

Finding: [ORG-PR-005](production-readiness/findings-register.md#org-pr-005).

---

## 1. Persistent-data inventory

Every store and state source the running platform touches, classified by what
losing it would mean. Classifications are read out of the repository, not
assumed.

| Store / state | Classification | Evidence | Backed up here |
| --- | --- | --- | --- |
| **PostgreSQL** | **Durable state — the system of record** | Every domain table lives here (`packages/db/src/schema/`): users, organizations, memberships, roles/permissions, plans and plan state, projects, API-key hash metadata, invitations, session and token lifecycle rows, security/audit events, and the Drizzle migration ledger. | **Yes** — this is the entire backup scope. |
| **Redis** | **Ephemeral operational state** | The only writes are `INCR` + `EXPIRE` on fixed-window rate-limit counters (`apps/api/src/lib/rate-limit.ts — createRedisRateLimiter`) plus a readiness `PING` (`apps/api/src/server.ts`). Every key is TTL-bounded and self-expiring. No session, token, queue, or business state. | **No, deliberately.** Losing Redis re-opens the current rate-limit windows and nothing else. Backing it up would create a second copy of security-relevant counters for no recovery value. |
| **Mailpit** | **Development-only state** | Local SMTP sink (`infra/docker-compose.yml`); production uses the SMTP driver, and no delivered message is a system of record. | **No.** |
| **API image / artifact** | **Rebuildable artifact** | Built from source by `apps/api/Dockerfile` + `apps/api/scripts/build.mjs`, resolved from `pnpm-lock.yaml`. | **No** — rebuild from a commit. |
| **Web image / artifact** | **Rebuildable artifact** | Built from source by `apps/web-demo/Dockerfile`. | **No** — rebuild from a commit. |
| **Logs** | **Operational evidence, not a restore source** | Structured logs go to stdout/stderr only; nothing writes a log file, and the production API image has no writable application path (`apps/api/Dockerfile`). | **No.** Logs are evidence for an investigation, never an input to a restore. |
| **Uploaded / object-storage state** | **Does not exist** | No upload route, no multipart handling, no object-storage client anywhere in `apps/` or `packages/`. `infra/compose.production-like.yml` declares no volumes. | Nothing to back up. |

**Contract — the durability boundary.** PostgreSQL is the only store whose loss
is unrecoverable. Everything else is either rebuildable from a commit,
regenerated by normal operation, or has no recovery value. A change that puts
durable state anywhere other than PostgreSQL invalidates this document and the
drills that depend on it.

## 3. Logical backup

```bash
pnpm db:backup                                    # uses DATABASE_URL / .env
pnpm db:backup -- --database-url "$PROD_URL" --output-dir /secure/backups
```

`tooling/db-backup.sh` runs `pg_dump --format=custom --compress=9 --no-owner
--no-acl` and writes three files:

```
orgistry-<UTC timestamp>[-<label>].dump         the backup (mode 600)
orgistry-<UTC timestamp>[-<label>].dump.sha256  integrity checksum
orgistry-<UTC timestamp>[-<label>].meta.json    provenance metadata
```

### Design choices

**Custom format (`-Fc`), not plain SQL.** It is compressed, restorable with
`pg_restore` into an empty database, and supports selective restore
(`pg_restore --table=...`) during an incident — the case where a plain SQL
dump is least useful.

**Client tools run in a pinned container.** `pg_dump`/`pg_restore` are
version-sensitive; a mismatch typically surfaces during a recovery, which is
the worst possible moment. Every client invocation runs from
`postgres:16.14-alpine` at the exact digest the repository's servers use
(`tooling/lib/pg-tools.sh` — `ORGISTRY_PG_IMAGE`, kept in sync with
`infra/docker-compose.yml`, `infra/compose.production-like.yml`, and the CI
service image). Docker is the only host prerequisite; no PostgreSQL
installation is needed or consulted.

*Rejected alternative:* use the host's `pg_dump`. It makes the artifact depend
on whatever a laptop or runner happens to have installed, and a dump taken by
a newer client than the restoring one can fail in ways nothing in this
repository would catch.

**The connection URL never becomes output.** It is passed to the client through
an environment variable, never as a command argument, never into a filename,
and never printed. Provenance metadata is read back from the server
(`current_database()`, `server_version`) rather than parsed out of the URL, so
no credential can reach `meta.json`.

**Failures are hard failures.** A `pg_dump` non-zero exit or a zero-byte output
deletes the partial file and exits non-zero. There is no partial-backup state
to mistake for a backup.

### Metadata sidecar

```json
{
  "artifact": "orgistry-20260824T061320Z.dump",
  "created_at": "2026-08-24T06:13:20Z",
  "database": "orgistry",
  "format": "pg_dump custom (-Fc, compress=9, --no-owner --no-acl)",
  "postgres_server_version": "16.12",
  "pg_dump_client": "pg_dump (PostgreSQL) 16.14",
  "client_image": "postgres:16.14-alpine@sha256:...",
  "applied_migrations": 13,
  "bytes": 53493,
  "sha256": "...",
  "encrypted": false,
  "note": "Contains user, organization, audit, password-hash, and token-hash data. ..."
}
```

`applied_migrations` is the row count of `drizzle.__drizzle_migrations`, so a
restored database can be checked against the schema generation it came from.
`encrypted: false` is stated explicitly — see §7.

## 4. Restore drill

```bash
pnpm drill:restore                    # data-layer verification
pnpm drill:restore -- --with-artifact # + the packaged API artifact
pnpm drill:restore -- --keep          # leave state behind for debugging
```

`tooling/db-restore-drill.sh` is the evidence that matters. A backup script
that has never been restored proves nothing, so the drill exercises the **real**
backup path — it calls `tooling/db-backup.sh`, not a drill-only copy of it.

### What one run does

1. creates a throwaway **source** PostgreSQL container and applies the
   migration baseline;
2. seeds deterministic synthetic Orgistry data
   (`tooling/fixtures/restore-drill-seed.sql`);
3. takes a backup with `tooling/db-backup.sh`;
4. asserts the artifact exists and is non-empty, verifies its SHA-256, **and**
   proves a truncated copy is rejected by `pg_restore` — corruption must fail
   loudly rather than restore partially;
5. starts a **fresh, empty target** container and asserts it has zero public
   tables *before* restoring, so a "successful" restore can never be reporting
   the target's own pre-existing state;
6. proves a **missing** artifact fails the same way: `pg_restore` against a
   path that does not exist exits non-zero, names the path it could not open,
   echoes no credential, and leaves the target with zero public tables. Probed
   on the real target immediately before the real restore, so "the target is
   still empty" is a meaningful assertion rather than a vacuous one;
7. restores with `pg_restore --exit-on-error`;
8. verifies the restored schema, the Drizzle migration ledger, and every seeded
   entity;
9. re-runs migrations against the **restored** database and requires the ledger
   to be unchanged — a restored database must be compatible with current
   migration handling;
10. with `--with-artifact`, exercises the packaged artifact (§5);
11. destroys every container, volume, network, and temporary file. The backup
    artifact never outlives the drill.

### Representative data

The fixture covers one row per entity class in the recovery contract: user,
organization, membership, role assignment, plan/entitlement state, project,
API-key hash metadata, invitation, security/audit events, and the `app_meta`
infrastructure marker. Roles, permissions, and plans are **not** re-created —
they are seeded by the migration baseline (migrations `0002`, `0003`, `0005`),
so the drill references them and thereby also proves the seeded baseline
survived.

Assertions go beyond row counts: an owner → membership → organization → plan →
project join must return the expected rows, and the API-key `secret_hash` and
`display_prefix` must match byte for byte — a restore that mangled hash-only
secret storage would silently break every machine credential.

### Fixture identity

Every drill identifier lives in `tooling/lib/restore-drill-fixture.sh` and is
passed into the seed SQL as psql variables, so there is exactly one definition.
The API-key `secret_hash` is **derived at run time** (`sha256_hex` in
`tooling/lib/pg-tools.sh`) rather than committed: a 64-hex constant in a
repository is indistinguishable from a real credential to a secret scanner, and
a derived value cannot drift from the secret it belongs to.

That derivation assumes the product hashes an API-key secret the same way. The
**contract test for that assumption is the authenticated read in §5**, not a
unit test: the seeded hash lets `GET /v1/external/projects` return the restored
projects only if the packaged API computes the same hash from the raw key, and
an unknown key must still return 401. If the product ever salted, peppered, or
changed algorithm, that request returns 401 and the drill fails. Because the
drill's hasher is a *shell* helper, an end-to-end assertion is also the only
one that actually exercises it.

`tooling/restore-drill-fixture.test.ts` therefore covers only what a running
drill cannot: that the raw key parses back through the product's `parseApiKey`
(a format break would otherwise surface as an unexplained 401), that the
fixture credential is obviously fake, that the drill derives its hash rather
than carrying one, and that no 64-hex hash literal is committed into either
tooling file. It deliberately does **not** re-derive the hash in TypeScript —
that compared Node's `createHash` against the product's `hashApiKeySecret`,
neither of which is the shell helper the drill uses, so it proved less than the
drill already proves while duplicating a cryptographic operation in test code
(and CodeQL read that duplicate as `js/insufficient-password-hash`).

## 5. Deployable-artifact compatibility

`--with-artifact` completes the recovery contract:

```
restored PostgreSQL
  → the artifact's own migration entrypoint (node dist/migrate.mjs)
  → the packaged API artifact (orgistry-api:production-like, NODE_ENV=production)
  → dependency readiness
  → GET /health   -> 200
  → GET /ready    -> 200
  → GET /v1/external/projects (API-key authenticated) -> the restored projects
  → node dist/retention.mjs (the packaged maintenance command)
```

The authenticated read is the strongest available application-level evidence,
and it is a real one: the external Projects API authenticates a Bearer API key
by SHA-256 hash lookup **against the restored database**, derives the tenant
from that key's row, and returns that organization's projects. One request
therefore exercises restored credential metadata, restored tenant state, and
restored business rows. The drill also asserts that an *unknown* key still
returns 401 — a restore must not widen authentication — and that no drill
secret appears in the artifact's logs.

*Why not a browser-session login?* Session authentication needs a real
Argon2id password hash, which cannot be produced from a SQL fixture without
duplicating the hashing implementation in the drill. API-key authentication is
deterministic SHA-256 (`apps/api/src/modules/api-keys/api-key-secret.ts`), so
the fixture can carry a real hash and the drift test can prove it stays real.

In this mode migrations run through `dist/migrate.mjs` rather than
`pnpm db:migrate`, so the drill needs no workspace install — which is why CI
can run it in the artifacts job straight after the image is built.

## 7. Backup security

A backup is the most concentrated copy of the platform's data that exists.
Treat one exactly as you would treat the production database.

**What a backup contains:** every user record and email address, every
organization and membership, the full security/audit event history, Argon2id
password hashes, SHA-256 refresh/verification/reset/registration token hashes,
SHA-256 API-key secret hashes, and invitation token hashes.

**Rules enforced by this repository:**

- **Never committed.** `.gitignore` excludes `backups/`, `*.dump`, and
  `*.dump.sha256`; `tooling/db-backup.sh` refuses to write inside a `.git`
  directory; the drills write to a temporary directory that is deleted on exit.
- **Never printed.** Nothing in the tooling writes backup CONTENT to any
  stream. CI steps print counts, sizes, and table names only.
- **Credentials stay out of paths and logs.** The connection URL is passed by
  environment variable, never as an argument or a filename component, and the
  metadata sidecar is built from server-side queries.
- **Restrictive permissions from creation.** The output directory is created
  under `umask 077`; the dump, checksum, and metadata files are `chmod 600`.
- **Backups are not debug artifacts.** A dump must never be attached to a
  ticket, pasted into a chat, or added to a CI artifact bundle. Reproduce a bug
  with synthetic data, as the drill does.

**Rules that are deployment responsibilities, stated honestly:**

- **The checksum is integrity, not encryption and not access control.** It
  proves an artifact was not truncated or corrupted in transit or at rest. It
  proves nothing about who can read it. This repository implements **no**
  encryption of backup artifacts, and adding a symbolic one so a document could
  claim "encrypted" would be worse than the current state — it would make an
  unverified claim reviewable as a verified one.
- **Production backup storage must use encryption at rest** (a managed
  database's own encrypted backups, or an object store with server-side
  encryption and a customer-managed key). That depends on infrastructure this
  repository does not provision (**ORG-PR-001**, open).
- **Production backup access must be least privilege** — a dedicated identity
  that can write backups and cannot read production, and a separate, audited
  path for restores. That depends on a secrets/identity story this repository
  does not have (**ORG-PR-006**, open).
- **Backup retention is a different policy from application-table retention.**
  How many backups are kept and for how long is a recovery-objective decision
  (see [production-target.md](production-readiness/production-target.md)).
  [retention.md](retention.md) governs rows inside a live database. Neither
  bounds the other: deleting aged rows does not shrink an old backup, and
  expiring old backups does not clean up a live table.

## 8. Known limitations

These remain open after Sprint 25 and are infrastructure-dependent, not
oversights:

- **No backup scheduler.** `tooling/db-backup.sh` is a command. Nothing invokes
  it on a schedule — there is no background runtime in this repository
  (**ORG-PR-016**, open). A real deployment uses its platform's scheduled-job
  facility or a managed database's built-in backup schedule.
- **No remote or encrypted backup storage.** Backups are written to a local
  directory the operator chooses. There is no upload, no lifecycle policy, no
  encryption at rest, and no cross-region copy (**ORG-PR-001**, open).
- **No provider-managed PITR.** The PITR capability proven in
  [pitr.md](pitr.md) is a locally-executed drill against locally-run
  PostgreSQL. A managed database's own continuous backup/PITR has not been
  configured or evidenced because no managed database exists here.
- **No production RPO/RTO evidence.** The drills prove recoverability of a
  fixture-sized database on a laptop and a CI runner. They say nothing about how
  long a real restore takes at production data volume, and no recovery objective
  has been measured against real infrastructure.
- **No restore rehearsal against real data.** By design — this repository has no
  production data.

## 9. Runbooks

All commands below are the actual repository commands and have been executed;
anything infrastructure-dependent is labelled.

### Take a logical backup

```bash
# Local development database (reads DATABASE_URL, falling back to .env)
pnpm db:backup

# An explicit target and destination
pnpm db:backup -- --database-url "postgres://user:pass@host:5432/orgistry" \
                  --output-dir /secure/backups --label pre-migration
```

Success prints the byte count, the applied-migration count, the server version,
and the artifact path (last line). Any connection or dump failure exits
non-zero and leaves no artifact behind.

### Verify a backup

```bash
cd /secure/backups
sha256sum --check orgistry-20260824T061320Z.dump.sha256   # Linux
shasum -a 256 --check orgistry-20260824T061320Z.dump.sha256   # macOS
cat orgistry-20260824T061320Z.meta.json
```

Then confirm it is actually readable — a checksum proves the bytes are intact,
not that PostgreSQL can parse them:

```bash
docker run --rm -v /secure/backups:/backups:ro \
  postgres:16.14-alpine pg_restore --list /backups/orgistry-20260824T061320Z.dump | head
```

### Restore a logical backup

**Restore into a fresh database — never over a live one.**

```bash
# 1. Create an empty target database.
createdb -h "$HOST" -U "$USER" orgistry_restored

# 2. Restore.
docker run --rm -v /secure/backups:/backups:ro \
  --env ORGISTRY_PG_URL="postgres://user:pass@host:5432/orgistry_restored" \
  --entrypoint sh postgres:16.14-alpine -c \
  'pg_restore --dbname="$ORGISTRY_PG_URL" --no-owner --no-acl --exit-on-error /backups/<artifact>.dump'
```

`--exit-on-error` is not optional: without it `pg_restore` continues past
failures and reports success on a partial restore.

### Validate restored Orgistry data

```bash
psql "$RESTORED_URL" -c 'SELECT count(*) FROM drizzle.__drizzle_migrations;'  # matches meta.json
psql "$RESTORED_URL" -c "SELECT to_regclass('public.users') IS NOT NULL;"
psql "$RESTORED_URL" -c 'SELECT count(*) FROM users;'
psql "$RESTORED_URL" -c "SELECT count(*) FROM roles WHERE key IN ('owner','admin','member','viewer');"
```

Then confirm migration compatibility — this must be a no-op:

```bash
DATABASE_URL="$RESTORED_URL" pnpm db:migrate
```

To rehearse the whole sequence end to end against synthetic data, run
`pnpm drill:restore -- --with-artifact`.

### Protect backup artifacts

- Store them outside the repository tree, on an encrypted volume, with
  restrictive permissions (the tooling already writes `600`).
- Never attach one to a ticket, chat message, screen share, or CI artifact.
- Delete drill and ad-hoc backups when finished: `shred -u <artifact>` on Linux,
  `rm -P <artifact>` on macOS.
- Rotate the database credential used for backups independently of the
  application credential once a secrets manager exists (**ORG-PR-006**, open).

### Handle a failed migration

**Not a rehearsed procedure — this is guidance, not evidence.** No migration
rollback has been executed against real infrastructure
(**ORG-PR-046**, open).

1. Stop deploying. The API does not migrate at boot
   (`apps/api/Dockerfile`), so a failed migration step leaves the previous API
   running against the old schema.
2. Read the migrator output. Drizzle applies migrations in order and records
   each one; a failure means the failing migration did not complete.
3. Do **not** hand-edit `drizzle.__drizzle_migrations`. A migration ledger that
   disagrees with the schema is worse than a failed migration.
4. If the schema is damaged, restore the pre-migration backup into a **new**
   database and cut over — this is exactly why §9 tells you to take a labelled
   backup before a migration.
5. If the change is time-sensitive and the data window matters, use PITR to a
   time just before the migration ([pitr.md](pitr.md)) rather than the last
   logical backup.

Forward-only migrations remain the repository's stated model: there are no
`down` migrations, and none should be invented during an incident.

### What remains infrastructure-dependent

Before any real deployment, the following must be arranged outside this
repository and are **not** evidenced here: a backup schedule, encrypted remote
storage with a lifecycle policy, least-privilege backup/restore identities,
provider-managed or self-managed continuous WAL archiving, measured RPO/RTO,
and a periodic restore rehearsal against production-sized data.
